> **v2.3.0 的稳定性补丁。** 同步 macOS 端 `fa6d9f3`（相对基线 `a649287`），修复 Windows Issue #10「服务不稳定」。v2.3.0 的全部功能原样保留。

## 修复 Issue #10「服务不稳定」（后端 Java，需重建 `astrostudyboot.jar`）

用户现象（v2.3.0）：DeepSeek 等 AI 流式分析「几句话之后就停止」；从旧版升级后排盘 / AI **间歇**报 `signature.error` / 「本地排盘服务未就绪」/ `predict/pd` statusCode 200 却报错。

**两个根因，均已治本：**

### (A) SSE emitter 线程不安全竞态 →「几句话之后停止」
v2.2.1（#8）引入的 15s keep-alive **心跳线程**与上游 **读流线程**并发调用非线程安全的 `SseEmitter.send()`；长流（如 `deepseek-reasoner`）下两者交错、或心跳失败时自行 `complete()` 抢先 → 读流下次 `sendEvent` 撞 `IllegalStateException: ResponseBodyEmitter has already completed` → 包成 RuntimeException → 流中途断。
- **修复**：`AIAnalysisProxyService` 新增线程安全 `SseChannel` 包装 emitter——**单锁串行化所有写**（心跳 + 内容）、`send/complete/completeWithError` **幂等**；心跳不再自行 `complete()`，收尾统一交主流程。`withHeartbeat / chatStream / stream{OpenAI,Anthropic,Gemini} / sendEvent` 全改走 channel。

### (B) SSE 标志跨请求污染 → 间歇 `signature.error` / 服务未就绪
`__sse__` 标志存在 **request 对象 attribute** 上，而 Tomcat **池化复用 request 对象**；上一个 SSE 请求残留的 `__sse__=true` 被后续排盘 / `predict` / 普通 AI 请求复用 → `complete()`/`afterCompletion` 的 `isSSE()` 误判 → 响应被当 event-stream 返回 → 前端报 `signature.error` / 未就绪。另：SSE async **re-dispatch** 时 request body 已被首次读取消费，用空 body 重算签名必然 `signature.error`。
- **修复**：`boundless/RequestHeaderInterceptor.preHandle` —— ① 仅对最初的 `DispatcherType.REQUEST` 做 body 解码 + 验签，async re-dispatch 直接放行不重复验签；② 每个新请求进来先 `TransData.setSSE(false)` 归零，堵死跨请求污染（真正的 SSE 端点之后自行 `SseHelper.push`→`setSSE(true)`）。

## 为何是 v2.3.1（不是覆盖 v2.3.0）
线上自 v2.2.1 起应用内自动更新已启用 → 已自动更新到 v2.3.0 的用户，**只有版本号变化**才会再收到推送。覆盖 v2.3.0 不会触发更新，故必须 bump v2.3.1。
