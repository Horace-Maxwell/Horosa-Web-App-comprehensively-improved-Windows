# Horosa v2.6.2 Beta — 发布说明

> **Windows 安装器专属补丁**：彻底修复 issue #18「升级安装从来都没有成功过，只能卸载之后再安装才能成功」。**纯 NSIS 安装器改动**（新增 `customUnInstallCheck` 钩子）——命盘计算 / 前端 / `astrostudyboot.jar` 与 v2.6.1 **逐字节一致**，v2.6.1 及更早全部功能原样保留。Mac 端无新提交（HEAD 仍 `fc7ab745b`），本版不涉及任何产品源同步。

## 背景：为什么 v2.6.0 的修复仍不够

v2.6.0 加了 `customCheckAppRunning`，在升级前强制结束正在运行的星阙（按映像名 `taskkill /F /IM Horosa.exe`，不带路径 / 用户名过滤）。但报告者反馈：**关掉程序、关机重启、再运行安装器，依旧报「Failed to uninstall old application files: 2」**。重启已证明没有任何星阙进程存活——所以「结束进程」这条路在他的场景里是空操作。

工程定位（electron-builder / app-builder-lib NSIS 模板逐行追踪）：那个 `2` 是**旧版本卸载器的退出码**，由 `handleUninstallResult`（`installUtil.nsh`）抛出。一次**原地升级**会先运行**当前已安装版本**的卸载器：

```
old-uninstaller.exe /S /KEEP_APP_DATA --updated _?=$INSTDIR
```

只要它返回非零，默认处理就 `SetErrorLevel 2; Quit`，**整个升级中止**。而这个旧卸载器是磁盘上已存在的二进制——由用户**当前所装版本**（通常早于 v2.6.0）打包，仍带着 electron-builder 的默认缺陷，v2.6.0 的修复只能改「新」安装器 / 卸载器，**改不到这个被迫调用的「旧」卸载器**：

- 它的强杀回退按 `/FI "USERNAME eq %USERNAME%"` 过滤——**中文 Windows 用户名**直接失配，杀不掉；和 / 或
- `un.atomicRMDir` 在中文安装路径 `…\星阙` 下，只要**任一文件**被安全软件（360 / Defender 实时扫描）、OneDrive 或开机自启的星阙短暂占用，就 `Abort` 返回非零。

重启也无效，正因为失败的不是「活进程」，而是旧卸载器自身的逻辑 / 文件锁。

## 修复（v2.6.2）：让安装器对失败的旧卸载器有韧性

`handleUninstallResult` 留了唯一一个钩子：**定义 `customUnInstallCheck` 后，它会被插入以替换默认的 `SetErrorLevel 2; Quit`**。我们接管这条失败路径（`desktop_installer_bundle/assets/installer.nsh`）：

- 旧卸载器返回 `0` → 一切照旧，什么都不做；
- 返回非零 → **不再中止**：先按映像名强杀残留星阙 + 仅清理本应用 `embedded-runtime` 目录下的 Java / Python（绝不动用户自己的 Java/Python），再**自行强制删除旧「程序目录」**（带重试，熬过杀软 / 句柄释放）后**继续安装**——新文件随即覆盖同一 `$INSTDIR`；
- 仅当目录确实含本应用 `Horosa.exe` 时才执行清理（避免误删无关目录）；**用户数据（userData / %APPDATA%）零影响**；
- 极端情况下文件被杀软死锁、重试仍失败：手动安装弹**明确可操作**的提示（关闭实时防护 / 手动删目录后「重试」），静默自动更新则给真实非零退出——**再不会**是那条看不懂的「code 2」。

因此**升级安装无需再先手动卸载**，且对中文用户名 / 中文安装路径 / 杀软占用都健壮。
